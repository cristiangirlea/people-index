# ADR 0001: Rust for the pipeline

Status: accepted, 2026-10-15

## Context

The pipeline's work is CPU-bound and repetitive: decompress gzip, split lines, parse JSON
envelopes, hash ids, compress segments with zstd, and assemble documents, for every record of
both feeds. Memory has to be bounded by configuration (partition size, buffers, concurrency)
so that a worker's container limit can be set with confidence. The same process also does a
lot of I/O concurrently: streaming objects from S3, uploading segments, and keeping several
bulk requests in flight against Elasticsearch, while renewing leases on a timer.

The crates have narrow contracts with each other (row types, the segment format, the stage
and executor traits), and a mistake at one of those seams silently loses or duplicates rows.

The candidates were Python, Go, a JVM dataflow engine (Spark or Flink), and Rust.

## Decision

Write every crate in Rust (edition 2024, MSRV 1.90, `unsafe` forbidden workspace-wide):

- **Throughput and memory control.** No interpreter or object overhead per record, no garbage
  collector pauses; a row is a struct, a JSON body is a byte vector. The record itself is kept
  as raw JSON (`serde_json::value::RawValue`) and only the fields the join needs are parsed, so
  unknown fields cost a copy, not a parse.
- **Async I/O with CPU work off the reactor.** tokio drives the store, Elasticsearch and lease
  traffic; gzip, JSON, zstd and the join run in `spawn_blocking` or rayon, connected by bounded
  channels, so back-pressure is structural.
- **Contracts in the type system.** Rows, task ids, stage names and errors are types shared
  across crates; `postcard` encodes the rows with serde, so the segment format follows the
  structs instead of a hand-maintained schema.
- **Deployment.** One binary in a distroless image (about 40 MB), running as a
  non-root user with a read-only root filesystem.
- **Libraries that fit**: `object_store` (S3, local and in-memory stores with conditional
  writes), `reqwest` with rustls, `zstd`, `flate2`, `xxhash-rust`, `clap` with `env`.

A JVM dataflow engine was rejected because it would bring its own cluster manager and state,
and the join here is simple enough to express as tasks over an object store. Python was
rejected for per-record CPU cost and memory per object at this volume. Go would have been a
reasonable choice; Rust was preferred for the absence of GC pauses, for zero-copy handling of
raw JSON, and for exhaustive matching over error and outcome enums.

## Consequences

- Compile times are long and the contributor pool is smaller than for Go or Python.
- Async Rust has sharp edges (cancellation, `Send` bounds across blocking work); the
  pipeline's task shape (async feeder, blocking worker, async uploader) is written once in
  `pi-stages` and reused by every stage.
- The MSRV is checked in CI so the toolchain floor is explicit.
- Performance is a design goal, not yet a measured fact: no benchmark has been run on this
  codebase (see the README's Limitations).
